# haiku-rails 共通ルール（すべての作業で守る）

## 進め方
- 作業は次の順に進める。段階ごとにスキルがある。
  1. 要件 `/req` → 2. 相談パケット `/consult`（必要なとき）→ 3. Opusに相談 `/opus-review`（ユーザーが打つ）
  → 4. 計画 `/task-plan` → 5. テスト `/write-tests` → 6. 実装 `/impl`（1タスクずつ）
  → 7. レビュー `/self-review` → 8. 仕上げ `/mr`・`/backlog-note`・`/explain`
- 小さな修正（1〜2ファイルで、テストで確かめられる）は、要件と計画を短く済ませてよい。段階を飛ばすときは、ユーザーに一言伝える。
- 作業の記録は、リポジトリ直下の `.rails/<YYYY-MM-DD>-<短い名前>/`（スキルの中で「作業フォルダ」と書いたらここのこと）に置く。`/clear` の後は、まずここ（requirements.md・plan.md）を読んで続きから始める。

## 守ること
- 推測で決めない。分からないことは質問するか、「不明：〜」と書く。
- 書く前に、似ている既存のコードを探し、そのやり方に合わせる。新しい書き方やライブラリを勝手に持ち込まない。
- 一度にやるのは計画の1タスクだけ。計画にない変更はしない。気づいたことは plan.md の「気づいたこと」に書く。
- 「できた」と言う前に、確認のコマンドを実際に実行して結果を見せる。実行していないものは「未確認」と書く。
- 同じエラーが2回続いたら、3回目は試さずに止まる。`/consult stuck` で詰まりメモを作り、ユーザーに報告する。
- テストを通すために、テストを書き換えない。テストがおかしいと思ったら、止まって理由を報告する。
- パスワード・トークン・個人情報を、ファイルやコマンドに書かない。

## 文脈（コンテキスト）を小さく保つ
- 大きなファイルは必要な範囲だけ読む。ログやテストの出力は、最後の数十行だけ見る。
- 1タスクが終わったら、ユーザーに `/clear` をすすめる（次は .rails/ から再開できる）。

## Opus について
- Opus を使うのは、ユーザーが `/opus-review` を打ったときだけ。自分から呼ばない。提案はしてよい。
- 提案してよい場面：タスクが決まったとき（進め方とテスト設計）、設計の分かれ道、同じエラーで2回詰まったとき、危ない変更（認証・権限・お金・データの削除や移行・同時実行・セキュリティ）を含むMRの前。
- `/opus-review` の答えが会話にあるのに、パケットと同じフォルダに `<パケット名>-answer.md` が無ければ、次に何かする前に全文を保存する（`/clear` で消えるため）。

## 答え方
- 日本語で、短く。結論を先に書く。
