# 解説ページを作る

読む人：この変更を初めて見る自分。用語の説明も要る。

対象：$ARGUMENTS（空なら、`.rails/` の一番新しいフォルダの plan.md と、ベースブランチとの差分）

## 手順

1. 対象を読む。差分なら `git diff --stat <ベース>...HEAD` で全体をつかみ、ファイルごとに読む。plan.md と review.md があれば読む。
2. 変更を「ブロック」に分ける。1ブロック＝1つの役割（関数1〜3個くらい）。**最大8個**。
3. `${CLAUDE_SKILL_DIR}/references/template.html` を読み、**`.rails/<作業>/explain.html`**（requirements.md と同じフォルダ。リポジトリ直下ではない）に書き、「（ここに〜）」を全部、実際の中身に置き換える。
   - CSS と全体の構成は変えない。ブロックの section は、ブロックの数だけ複製する。
   - コードは、実際のコードをそのまま貼る（書き換えない・省略するなら「…」と書く）。`&` `<` `>` は `&amp;` `&lt;` `&gt;` にする。
   - 図は Mermaid で書く。全体図には、変更した部分に色（`class X changed`）をつける。
   - 用語は、出てきたブロックで1行説明し、用語集にもまとめる（五十音順）。このコードでの意味も書く。
4. **事実の確認（いちばん大事）**
   1. ページに書いた事実（ファイル名・行・関数名・引数・戻り値・動き・テストの場所）を、全部一覧にする。
   2. 1つずつ、実際のコードを読んで確かめる。違っていたら直す。
   3. 確かめられないものは消すか、「未確認」と書く。
   4. 「7. 確認したこと」に件数を書く。
5. 「（ここに」が残っていないか検索して確かめる（残っていたら埋めるか、その行を消す）。
6. ファイルのパス（`.rails/` の中にあること）と、ブロックの数・確認した件数をユーザーに伝える。

## 守ること

- 推測で書かない。「たぶん」と思ったら、コードを読んで確かめる。
- 外部から読み込むのは Mermaid だけ（ひな形のとおり）。ほかのライブラリや画像を足さない。
- パスワード・トークン・個人情報が入ったコードは貼らない（その部分は「（秘密情報のため省略）」にする）。
