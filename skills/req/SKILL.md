# 要件を整理する

入力：$ARGUMENTS

入力が空なら、「何をしたいか（課題の本文かURL）」をユーザーに聞いて止まる。

## 手順

1. 作業フォルダを作る：リポジトリ直下に `.rails/<今日の日付 YYYY-MM-DD>-<英小文字とハイフンの短い名前>/`。
   - `.rails/.gitignore` が無ければ、中身を `*` の1行にして作る（これで `.rails/` の中は git に入らない。リポジトリの .gitignore は触らない）。
2. 入力を読む。URLなら、使えるツール（Backlog の MCP など）で本文を取る。取れなければ、本文を貼ってもらうよう頼んで止まる。
3. 関係しそうなコードを探す（Grep・Glob）。読むのは、場所を特定できる範囲だけ。見つけたファイルと関数を「関係する場所」に書く。
4. 下の形で `requirements.md` を書く。
5. 「不明点」が1つでもあれば、番号つきの質問としてユーザーに聞き、**答えをもらうまで次へ進まない**。答えをもらったら requirements.md に書き足し、不明点から消す。
6. 最後に次の一歩をすすめる。
   - 中くらい以上の作業（1日以上・3ファイル以上・危ない変更を含む）：「`/consult plan` で相談パケットを作り、`/opus-review` で進め方とテスト設計を相談するのがおすすめです」
   - 小さな作業：「`/task-plan` で計画を作ります」

## requirements.md の形

```markdown
# 要件：<一行で>

## 目的（なぜやるか）

## やること
- 

## やらないこと
- 

## 受け入れ条件（確かめられる形で）
- [ ] <〜のとき、〜になる>

## 不明点（質問）
1. 

## 関係する場所
- <ファイル>：<関数・役割>

## 関連リンク
- <課題のURL・課題キー・資料>
```

## 守ること

- 受け入れ条件は、テストか手で確かめられる形にする。「使いやすくする」「速くする」のような書き方はしない（数字や具体的な動きにする）。
- ユーザーが書いていないことを「やること」に足さない。足したほうがよいと思ったら「不明点」に質問として書く。
- 数字（上限・金額・件数など）は、入力に書いてあるものだけ使う。書いていなければ不明点にする。
