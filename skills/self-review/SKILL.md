あなたは、この変更を初めて見るレビュアー。会話の経緯は知らない。

対象：$ARGUMENTS（空なら、リポジトリ直下の `.rails/` で一番新しいフォルダ）

## 手順

1. 対象フォルダの requirements.md と plan.md を読む。
2. ベースブランチを調べる（`git symbolic-ref --short refs/remotes/origin/HEAD`。だめなら `main`、それも無ければ `master`）。
3. 差分を見る：`git diff --stat <ベース>...HEAD` で全体をつかみ、ファイルごとに `git diff <ベース>...HEAD -- <ファイル>` を読む。
4. 次の観点を、上から順に1つずつ確かめる。**指摘には必ず根拠（ファイル:行）をつける。根拠を示せないものは書かない。**
   1. 受け入れ条件：1つずつ、満たしているか。どのテストで確かめているか。
   2. 計画とのずれ：計画に無い変更、やり残しのタスク。
   3. 境界・異常系：空・0・null・上限・エラーのときの扱い。
   4. 危ない変更：認証・権限・お金・データの削除や移行・同時実行・入力チェック。
   5. テスト：仕様を確かめているか（実装の結果をなぞっているだけでないか）。テストケース表と合っているか。
   6. 読みやすさ：名前、重複、お手本とのやり方の違い。（テスト名の先頭の `No◯` はテストケース表との対応を示す決まりなので、指摘しない）
5. テストを全部実行し、結果（件数・失敗）を書く。出力は最後の数十行だけ見る。
6. 対象フォルダに `review.md` を書く（形は下）。コードは直さない。
7. 判定と「直すべき点」の件数を返す。

## review.md の形

```markdown
# セルフレビュー：<要件の一行>

## 判定：出してよい / 直してから / 相談が必要

## 受け入れ条件
- [x] <条件>：<確かめているテスト or 根拠>
- [ ] <条件>：<足りない理由>

## 直すべき点（重い順）
1. <ファイル:行>：<何が問題か>／<直し方>

## 気になる点（直さなくてもよいもの）

## テストの結果

## 危ない変更
<あれば。あれば「/consult risk → /opus-review をすすめる」と書く>
```
