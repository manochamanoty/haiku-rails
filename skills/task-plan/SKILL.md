# 実装計画を作る

## 手順

1. 作業フォルダ（`.rails/` の一番新しいもの、またはユーザーが指定したもの）の requirements.md を読む。
   - 「不明点」が残っていたら、先にユーザーに聞いて止まる。
2. Opus の答えを確かめる。
   - 直前の会話に `/opus-review` の答えがあり、同じフォルダに `<パケット名>-answer.md` が無ければ、**まず答えの全文をそのファイルに保存する**（`/clear` すると消えるため）。
   - `consult-plan-*-answer.md` があれば読み、その「進め方」と「テストケース表」を土台にする。変えるときは plan.md の「方針」に理由を書く。
3. 関係するコードを読み、**お手本**を決める：似ている既存の実装を1つ、既存のテストを1つ。
4. タスクに分ける。
   - 1タスク＝1コミット。触るファイルは3つまで。
   - 順番は「先に土台（型・関数）、後で呼び出す側」。
   - テストを書く作業はタスクに入れない（/write-tests でまとめて書く）。
5. テストケース表を作る。Opus の答えがあればそのまま使う。無ければ下の決まりで作る。
6. `${CLAUDE_SKILL_DIR}/references/example-plan.md` を読み、**同じ細かさ**で `plan.md` を書く（形は下）。
7. ユーザーに「タスク◯個・テストケース◯件。次は `/write-tests`」と伝える。

## 1タスクの書き方（すべての項目を埋める）

```markdown
- [ ] T1：<何をするか>
  - 触るファイル：<パス>
  - お手本：<似ている既存コードの ファイル:関数>
  - やること：<関数名・引数・戻り値・中の処理を具体的に>
  - 対応するテスト：<テストケース表の No>
  - 確認コマンド：<実際に打つコマンド>
  - 終わりの条件：<確認コマンドが通る、など>
```

## テスト設計の決まり

1. 正常系：関数ごとに代表を1つだけ
2. 境界値：上限・下限の「ちょうど」「1つ手前」「1つ先」
3. 空・0・null・最大の長さ・重複・順番違い
4. 異常系：エラーになるべき入力と、そのときのエラーの種類
5. 分岐：仕様の「〜の場合」の両側

- 通って当たり前のケース（値を入れて取り出すだけ、型が合うだけ）は書かない。
- 期待値は仕様（requirements.md）から決める。実装を想像して決めない。決まらないものは「仮定：」をつけ、ユーザーに確かめる。
- 各ケースに、受け入れ条件のどれを確かめるかを書く。

## plan.md の形

```markdown
# 計画：<要件の一行>

## 方針（3行まで）

## テストの実行方法
- 全部：<コマンド>
- 1ファイル：<コマンド>

## テストケース表
| No | 対象 | 観点 | 入力 | 期待する結果 | 仕様のどこ |

## タスク
- [ ] T1：…

## 気づいたこと（計画の外で、直したほうがよいもの。実装中に追記）

## 実装メモ（実装中に追記）
```
